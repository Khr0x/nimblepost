# NimblePost releases

Changesets 3.0.1 manages the desktop version and changelog, following Fevex's
version-PR workflow. The desktop package stays private; nothing is published to
npm. The macOS prerelease is published on GitHub after its build is verified.

## Add a release note

Run `npm run changeset`, select `@nimblepost/desktop`, choose the SemVer impact
(`patch`, `minor` or `major`) and describe the change. Commit the generated
`.changeset/<name>.md` with the source changes. Docs-only or test-only changes do
not need a version bump.

The repository is in `alpha` prerelease mode. Changesets owns the counters; do
not edit package versions, `pre.json` or `release-plan.json` manually. Consumed
changesets move into `.changeset/pre/` and do not create another release.

## From changes to a downloadable release

1. A push to `main` runs CI and creates or updates `changeset-release/main`.
2. That PR runs `npm run ci:version`, generating the desktop version, changelog,
   Tauri config, Rust workspace version, both lockfiles and a release plan.
3. Review and merge the version PR separately from source changes.
4. CI validates the merged version-only plan. The macOS job builds a universal
   app and DMG for Apple Silicon and Intel, then checks the signature, binary
   architectures and disk image.
5. Only after verification, it creates `v<version>`, attaches the DMG and
   publishes the GitHub prerelease with the generated changelog and installation
   instructions. No manual tag push is needed.

The initial patch changeset advances `0.1.0` to `0.1.1-alpha.0`. Future ALPHA
numbers are generated by Changesets. An existing published release is preserved;
a retry can finish uploading an incomplete draft for the same commit. A tag
pointing to a different commit is rejected.

## GitHub setup

Enable **Settings → Actions → General → Allow GitHub Actions to create and
approve pull requests** so Changesets can open the version PR.

As in Fevex, a GitHub App is optional: configure the repository variable
`RELEASE_APP_ID` and secret `RELEASE_APP_PRIVATE_KEY`. The app needs Contents and
Pull requests write access to NimblePost. Its token allows generated version PRs
to trigger CI automatically. With the default `GITHUB_TOKEN`, those bot-generated
PR events do not trigger another workflow; run CI manually on the version branch
before merging. The push after a human merges the PR always runs the release CI.

An ordinary source push only updates the version PR. **Changesets releases →
Run workflow** on `main` validates the project without creating a version PR,
tag or release. To retry publication, rerun the failed release run for the same
commit.

## Local checks

```sh
npm run changeset -- status
npm run release:check
npm test
```

`npm run ci:version` writes generated versions and consumes pending changesets;
automation normally runs it in the version PR. The release tooling tests perform
this operation in temporary repositories and leave this checkout's versions
unchanged.
